## Persisted document store + read-back + source-file viewer (spec 0006 / ADR-0018)
**TL;DR:** Added a `Document` persistence layer (original file + metadata + fields) as a new `IDocumentStore` port with in-memory + Azure Blob adapters; new `GET /documents`, `GET /documents/{id}`, `GET /documents/{id}/file`; `Citation` gains `source`; frontend gains a persisted documents table + a modal viewer that embeds the original file, and citations link to their source document.
Tags: #document-store #blob #ports-adapters #frontend · Notes touched: —
Evidence: [[knowledge/docs/specs/0006-document-read-back-list-view-original-file]] · [[knowledge/docs/decisions/0018-persisted-document-store-azure-blob-for-original-files-and-metadata]] · PR #34 · `2ba0fa5`,`766443f`,`aeafc1a`,`4f945ba`,`d242f27`

### Decisions
- **Decision:** A **new `IDocumentStore` port** (sibling to `IVectorStore`), not an extension of it — vector store is a similarity index, document storage is object storage (PDF bytes don't belong in the 50 MB Free-tier search index). Two blobs per doc (`"{id}"` bytes + `"{id}.json"` metadata); list enumerates `*.json`. (ADR-0018)
- **Decision:** Blob auth is **managed-identity-preferred** (`Blob:ServiceUri` + `DefaultAzureCredential`) with a **connection-string fallback** (`Blob--ConnectionString`, already in KV). Config-selected via `DocumentStore:Provider` (default `azureblob`, made explicit in `appsettings.json`).
- **Decision:** Document persistence is **required** at ingest (a store failure fails the write path) — unlike best-effort field extraction — because "view source" depends on it.
- **Decision:** The viewer embeds the original file via a same-origin `/documents/{id}/file` URL in an `<iframe>` — exposed as a pure `documentFileUrl(id)` string helper so bytes never pass through `fetch`/`ApiResult` (keeps the single-typed-client invariant).

### Findings / remember
- **Finding:** Infra was already provisioned (storage `stlanddochr01` + container `documents`, `Blob--ConnectionString` in KV; AZURE-CONFIG §6.4 named it) — so this wired an adapter to existing infra, no new resource. The only new live step is granting the app MI **Storage Blob Data Contributor** for the passwordless path.
- **Finding:** The live default falls through cleanly: `DocumentStore:Provider` defaults to `azureblob`, the ctor uses `ConnectionString` from KV when `ServiceUri` is unset — so it comes up on Blob with zero extra env on next deploy.

### Changes
- **Backend:** `Storage/{IDocumentStore,DocumentMetadata,DocumentFile,InMemoryDocumentStore,AzureBlobDocumentStore}.cs`, `Model/BlobOptions.cs`; ingest persists the document; `Citation` + `AskEndpoints` carry `source`; `Program.cs` provider switch; `Azure.Storage.Blobs` 12.29.0; `TestModuleInitializer` pins `DocumentStore__Provider=inmemory`. Tests: `DocumentStoreTests`, `DocumentReadEndpointTests`, extended `AskEndpointTests`.
- **Frontend:** `api/{client,types}` (`listDocuments`/`getDocument`/`documentFileUrl`, `DocumentSummary`, `Citation.source`); `ui/{useDocumentTable,DocumentsTable,DocumentViewer}`; `Answer`/`AskPanel`/`App` wiring; CSS. 51 FE tests green (typecheck + build).

### Open threads
- **Backend not built/tested in this env** (no .NET SDK; MS hosts 403) — relies on CI / local `dotnet test`.
- **Lock-file regen still pending:** `Azure.Storage.Blobs` added → `cd backend && dotnet restore --force-evaluate` + commit before CI's locked-mode restore passes.

## Multi-select document delete (spec 0008 / ADR-0019)
**TL;DR:** `DELETE /documents/{id}` removes a document from **both** stores (chunks + file/metadata), idempotent → 204; documents table gains per-row + select-all checkboxes and a confirmed "Delete selected".
Tags: #delete #ports-adapters #consistency #frontend · Notes touched: —
Evidence: [[knowledge/docs/specs/0008-delete-documents-multi-select]] · [[knowledge/docs/decisions/0019-hard-best-effort-non-transactional-document-deletion]] · PR #34 · `c23be37`,`a8dd24e`

### Decisions
- **Decision:** Deletion is **hard, best-effort, non-transactional** across the two independent stores, with **idempotency** as the convergence guarantee (retry the same DELETE; `204` whether or not the id existed). A mid-delete failure can orphan one side; no saga/soft-delete/undo. (ADR-0019)
- **Decision:** Additive port extensions (`IVectorStore.DeleteByDocumentAsync`, `IDocumentStore.DeleteAsync`) recorded in spec 0008 (within ADR-0017/0018); **per-id** endpoint with the UI looping for multi-select (bulk endpoint deferred).

### Findings / remember
- **Finding:** Azure AI Search deletes only by **index key** (chunk id), not by filter — to delete all chunks for a `documentId`, query the keys first (the field is filterable) then `IndexDocumentsBatch.Delete("id", keys)`.

### Changes
- **Backend:** delete methods on both ports + all four adapters (in-memory remove; Search query-keys-then-batch-delete; Blob `DeleteIfExists` on both blobs); `DELETE /documents/{id}` endpoint. Tests: `InMemoryVectorStoreTests`, `DocumentDeleteEndpointTests`, extended `DocumentStoreTests`.
- **Frontend:** `deleteDocument` client method; selection + confirmed delete in `DocumentsTable`; `App` deletes each id, closes the viewer if it showed a deleted doc, reloads. 77 FE tests green.

### Open threads
- Optional bulk `POST /documents/delete` (one round-trip / atomic confirm) — noted out of scope in spec 0008.
- Azure delete uses one `Size`-bounded key query per document; paging is a future refinement for very large docs.

## LLM usage & cost ops dashboard (spec 0009 / ADR-0020) + live-metrics fix
**TL;DR:** New operator-facing **Ops / Usage** tab + `GET /usage` reading **Azure Monitor platform metrics** for the Foundry resource via a new config-selected `IUsageSource` port; cost **computed** from a non-secret price table. Shipped (#40, merged), Azure-wired by hand, then fixed a live bug where everything but request-total read zero (#42).
Tags: #backend #frontend #azure #observability #cost #metrics · Notes touched: [[azure-monitor-usage-metrics]]
Evidence: [[knowledge/docs/specs/0009-llm-usage-and-cost-ops-dashboard]] · [[knowledge/docs/decisions/0020-llm-usage-cost-observability-azure-monitor-metrics]] · PR #40 (merged) / `feat/llm-dashboard` · PR #42 / `fix/usage-azure-monitor-metrics`

### Decisions
- **Decision:** Source the dashboard from **Azure Monitor platform metrics only**, behind a new `IUsageSource` port (`UsageSource:Provider` = `azuremonitor` live / `inmemory` offline-test) — free, read-only, $0 infra; cost is **computed** (tokens × price table) by a **pure calculator outside the adapter** so it's provider-independent + unit-tested (ADR-0020). Platform metrics can't attribute tokens to an app feature — that's a future App Insights OTel upgrade.
- **Decision:** Distinct **operator** audience from the analyst Dashboard → its own tab + endpoint, not an extension of `/documents` aggregation.
- **Decision:** Auth via the app's **managed identity** (`Monitoring Reader`, read-only least-privilege) — **no new secret**; `Monitor:ResourceId` + the `Pricing:` table are **non-secret** config (env / appsettings, NOT Key Vault).
- **Decision:** Removed the **"record types for DTOs"** convention from CLAUDE.md (+ ARCHITECTURE mirror) — config **Options** bind via `ConfigurationBinder` and need settable props, so they stay `sealed class` (matching the 8 existing `*Options`); the genuine DTOs already are records. (Followed a code-review false-positive on `MonitorOptions`/`DeploymentPrice`.)

### Findings / remember
- **Finding:** Azure Monitor returns split-dimension metadata keys **lower-cased** (`modeldeploymentname`, `statuscode`) and `MetricTimeSeriesElement.Metadata` is a **case-sensitive** dictionary — so a CamelCase `TryGetValue` drops every split series. This was the prod bug: tokens/per-deployment/status all 0 while **request Total still showed** (it sums unconditionally before the metadata check). Fix: `MetricMetadata.TryGetDimension` (OrdinalIgnoreCase).
- **Finding:** The live resource is an **AIServices (Foundry)** account whose metric names differ from classic Azure OpenAI — latency is **`Latency`**, not `AzureOpenAITimeToResponse` (which returned no data). Token metrics `ProcessedPromptTokens`/`GeneratedTokens` exist and have data. Always check `az monitor metrics list-definitions` against the actual resource kind.
- **Finding:** The live adapter is **not exercised by CI** (tests pin `inmemory`), so name/casing mismatches only surface against the real resource — the gold-standard verify is running the API locally against Azure (`az login` + `Monitor__ResourceId`) and curling `/usage`.
