# CI PR review (GitHub Actions)

How automated PR review is wired in this repo. Set up 2026-06-07.

## The two workflows (on `main`)
Both generated by `/install-github-app` (the Claude GitHub App's setup PR), using
`anthropics/claude-code-action@v1`:

- **`.github/workflows/claude.yml`** ("Claude Code") — the **interactive `@claude` assistant**.
  Triggers on `issue_comment` / `pull_request_review_comment` / `pull_request_review` / `issues:[opened]`
  whose body/title contains `@claude`, **gated to trusted `author_association`** (OWNER/MEMBER/
  COLLABORATOR). **Mention-triggered, not assignee-triggered.** Runs with **full-pickup writes**
  (`contents` + `issues` + `pull-requests: write`) so it can branch, commit, open PRs, and reply.
- **`.github/workflows/claude-code-review.yml`** ("Claude Code Review") — the **automatic reviewer**.
  Triggers on `pull_request` (opened/synchronize/ready_for_review/reopened) and runs the official
  **code-review plugin** (`prompt: /code-review:code-review --comment <repo>/pull/<n>`). The
  **`--comment` flag + `pull-requests: write`** are what make it post inline; it is deliberately
  **not** given `contents: write` (it comments, never pushes). Reviews every PR.

## Auth
- Credential is the **Claude Max OAuth token**: `secrets.CLAUDE_CODE_OAUTH_TOKEN`, minted with
  `claude setup-token` (≈1-year token). **Not** an `ANTHROPIC_API_KEY` (that's a separate
  console pay-per-use credential). See `CONTRIBUTING.md` for the surrounding branch/PR workflow.
- GitHub **secrets are per-repo** — a token set in another repo doesn't carry over.
- Installing the GitHub App (repo permissions) is **separate** from the credential secret; both
  are required. Subscription OAuth tokens for unattended CI are a ToS/usage gray area vs. the
  API-key path — fine here, worth knowing.

## Permissions — the templates ship read-only
`/install-github-app` scaffolds both jobs **read-only** (`pull-requests: read`, etc.), so they run
**green but post nothing** until widened — the run log shows `permission_denials` and, for the
reviewer, "No buffered inline comments":
- **Reviewer** needs `pull-requests: write` **and** the plugin's `--comment` flag (both, or it reviews
  silently). Never give it `contents: write`.
- **`@claude`** needs `contents` + `issues` + `pull-requests: write` to deliver/reply; read-only lets it
  read a mention but neither answer nor push.
- With writes granted, gate triggers on **`author_association`** so only trusted users can drive the
  agent — and listen to **`issues:[opened]` only**: keying the gate on `issue.author_association`
  while also firing on `assigned` re-runs Claude on any reassignment of a trusted-author `@claude` issue.

## Gotchas
- **A new/edited review workflow SKIPS on its own introducing PR** (a workflow-validation guard:
  the file must match the copy on the default branch). The check goes **green but didn't run** —
  it only activates after merge to `main`, so the **first real review is the next PR**. Verify the
  run log / PR comments, not the checkmark.
- A hand-rolled review workflow + `/install-github-app` = duplicate reviewers (double comments).
  Let the App scaffold the workflows; don't pre-author one. (We removed a duplicate in PR #3.)
- Public repo: fork PRs don't get secrets under `pull_request`, so a fork PR would run with an
  empty token. The App's `claude-code-review.yml` does not guard forks — add an
  `if: …head.repo.full_name == github.repository` if external PRs start arriving.

## Issues as a tracker (adopted 2026-06-07)
Reversing the earlier "no issues" stance: spec-derived work is now tracked as **GitHub issues**
created by **`/issues`** from an accepted spec (the spec→issue→PR→review loop). Each issue carries the
spec + doc references and its dependencies as body text (`Blocked by: #N`) — native blocked-by links
aren't settable via the GitHub tools/`gh`, only the UI. Review still happens on the PR (the reviewer
above) plus the local `/code-review` skill in-session.
